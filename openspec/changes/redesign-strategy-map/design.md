## Context

Two days ago we shipped `strategy-map-on-demand` (PR #285, then production
PR #291) and `decompose-strategy-map-synthesis` (Phase 1 + Phase 2, also
prod PR #291). The combination put the strategy-map artifact behind a
user-clicked CTA at Beat 6 of the analysis page, generated by a
dedicated SQS-driven worker Lambda using the decomposed call shape
(~45 s end-to-end).

Production usage surfaced that the on-demand model wasn't the right
product fit:

- Users want the strategy map as part of the headline output, not as
  an opt-in artifact behind another click + wait.
- The strategy map is the most synthesised view of the company — it
  should be presented prominently, not buried at Beat 6.
- The "Want a deeper analysis?" CTA at Beat 4 + the "Dig deeper with
  Sc0red advisor" CTA below the map = two CTAs for one intent.
- The K&N "What's Missing" gaps section blurs into the risks section
  in the AI's output. Removing it tightens the narrative.
- The 2D React Flow canvas renders chips that overflow their
  perspective bands when a theme has many objectives. This was
  acceptable as a beta but isn't acceptable as the centerpiece.

Additionally, two layers of legacy code accumulated during the rollout:

- **Layer A**: the on-demand worker, SQS queue, dedicated Lambda, API
  endpoint, frontend CTA components, AppSync subscription wiring.
- **Layer B**: the Phase 1/Phase 2 feature flags
  (`GENERATE_STRATEGY_MAP_DECOMPOSED`,
  `GENERATE_STRATEGY_MAP_DECOMPOSED_SYNTHESIS`) plus
  `_strategy_map_legacy_steps.py` — kept as fallback during the
  decomposed-path rollout, now safe to delete after the prod soak.

This change is the consolidation: re-position strategy map in the
narrative, fix its visual quality, drop the noisy gap section,
re-integrate it into the analysis pipeline, and clear both legacy
layers in one coordinated effort.

## Goals / Non-Goals

**Goals:**

- Strategy map is auto-generated as part of the analysis pipeline (no
  user click required), as the last step before `PersistResults`.
- Strategy map renders at Beat 3 of the analysis-detail page,
  immediately after Top 3 Immediate Actions.
- `Sc0redCTABanner` moves to Beat 4 immediately after the strategy
  map and renders expanded by default.
- `DeepDiveCTA` and the "Dig deeper with Sc0red advisor" copy are
  removed.
- The `whatsMissing` / gaps content is removed end-to-end (Pydantic
  model, JSON schema, prompt template, AI call, frontend rendering).
- The 2D React Flow canvas layout is reworked so chips never overflow
  bands; text truncation is responsive; visual quality is
  professional.
- The on-demand SQS+Lambda+API+frontend-CTA infrastructure is deleted.
- The Phase 1/Phase 2 feature flags and the legacy monolithic fallback
  paths are deleted.
- Analyses persisted before this change can be regenerated to gain a
  strategy map via an inline "Regenerate" affordance.

**Non-Goals:**

- Changing the strategy-map content semantics (perspective definitions,
  objective categories, value-proposition archetypes, arrow direction
  rules) — all unchanged.
- Re-introducing the on-demand pattern for other artifacts. This
  change is strictly a revert of the on-demand model FOR THE STRATEGY
  MAP and a cleanup of accumulated cruft.
- Bulk-backfilling strategy maps for all existing analyses. The user
  is the only production consumer at this point; an inline regenerate
  affordance is sufficient.
- Migrating the persisted `whatsMissing` data on existing analyses.
  Pydantic accepts extra fields by default; old data continues to
  load.
- Building diligence mode or any further analysis surfaces. Out of
  scope.

## Decisions

### 1. Pipeline integration as a sequential final step (Option A)

**Decision**: Re-add `GenerateStrategyMap` as the final pipeline step
before `PersistResults` in the company analysis pipeline.

**Alternatives considered**:

- **Option B — Trigger from scan-complete event**: keep the on-demand
  worker; the analysis worker enqueues a strategy-map job after
  `PersistResults`. User sees analysis-detail page before the strategy
  map is ready; AppSync push fills it in.
  Rejected: keeps the on-demand worker alive, preventing the legacy
  cleanup. Two-stage rendering is also worse UX (page loads with an
  empty slot, then fills).
- **Option C — Parallel branch with `PersistResults`**: fan out to a
  strategy-map subroutine in parallel with the persist step. Same
  total scan wall-clock as today.
  Rejected: most complex orchestration. The 25 s net latency increase
  (35 s strategy map - 10 s gaps savings) is acceptable; the
  simplicity of Option A wins.

**Why this works**: the existing decomposed `GenerateStrategyMap` is
already a `RequestStep` subclass. Adding it to the pipeline-step list
in the company-analysis factory is a small additive change. The
analysis worker absorbs the strategy-map AI calls within its existing
Lambda envelope. Saves one Lambda (the dedicated strategy-map worker)
and one SQS queue from infrastructure.

### 2. Beat-order: strategy map at Beat 3, CTA at Beat 4 expanded

**Decision**: Reorder the analysis-detail beats:

```
Beat 1: Hero (company name, risk tier, etc.)
Beat 2: Top 3 Immediate Actions
Beat 3: Strategy Map  ← was Beat 6
Beat 4: Sc0redCTABanner "Want a deeper analysis?" — EXPANDED by default
Beat 5+: EBITDA Tree, Opportunities, Risks, Value Chain, etc.
```

**Why this order**: the strategy map is the highest-synthesis artifact
the analysis produces. Placing it right after the call-to-action top
list creates a visual hierarchy that mirrors what an analyst would
want to see first. Placing the deep-dive CTA immediately after the
strategy map captures the user at peak interest — they've just been
shown the most impressive synthesis, and the ask follows.

**Why "expanded by default"**: the legacy `Sc0redCTABanner` rendered as
a small inline banner (collapsed state). At Beat 4, immediately after
the strategy map, it should fill more visual real estate — showing the
full value proposition for a deep-dive, not just a compact CTA bar.
Defaults to expanded; remains dismissible.

### 3. What's Missing — hard removal end-to-end

**Decision**: Remove `whatsMissing` from generation, schema, Pydantic
model, prompt template, AI call, and frontend rendering.

**Alternatives considered**:

- **Soft removal — keep generation, don't render**: keeps the AI call
  and downstream data alive in case a future surface (PDF export,
  diligence mode) wants to use it.
  Rejected: dead data is a maintenance burden. The K&N gap concept
  can be re-introduced later as a separate change if a real use case
  emerges; until then the simpler model wins.

**Impact on the strategy-map AI prompt**: the existing arrows-and-gaps
flow generates priorities + arrows + gaps in parallel. Dropping gaps
saves one AI call (the `ai_call_gaps` singleton, ~10 s wall-clock at
the slowest tail). The remaining `ai_call_priorities` and the arrows
yes/no bank are unchanged.

**Migration**: old persisted analyses may have `whatsMissing` data on
the `StrategyMap` JSON blob. Pydantic with `extra="allow"` (or the
default behaviour) will load them without error. The frontend simply
won't render the section.

### 4. React Flow canvas layout overhaul

**Decision**: Rework `frontend/src/components/strategy-map/` layout to
guarantee:

- Each perspective band's height scales to fit the maximum number of
  objectives across themes within that band.
- Chips never overflow vertically into adjacent bands.
- Chip widths respect the available horizontal space; text truncation
  is responsive (not a fixed character cutoff).
- The band labels (FINANCIAL, CUSTOMER, INTERNAL PROCESSES,
  ORGANIZATIONAL CAPACITY) and their secondary labels render without
  overlapping any chip.

**Approach**: replace the current static-coordinate layout with a
measure-first, render-second pass:

1. Compute the per-band objective count (max across themes for
   internal processes).
2. Compute the band heights from that count + the per-chip target
   height + per-row gap.
3. Compute chip positions within each band using row/column indices.
4. Render via React Flow with the computed positions and a custom
   chip node component that does responsive text truncation
   (CSS `text-overflow: ellipsis` with the chip's actual width, not
   a character cap).

**Alternatives considered**:

- **Move to CSS Grid (drop React Flow)**: React Flow is what enables
  the arrow rendering (cause-and-effect edges between chips). Without
  it, we'd need to re-implement arrow drawing.
  Rejected: too much scope. Keep React Flow; fix the node layout
  computation.

### 5. Backfill UX: inline "Regenerate" affordance

**Decision**: Analyses persisted before this change have no
`strategyMap` field on the assessment record. The analysis-detail page
detects this case and renders a "Regenerate strategy map" button at
Beat 3 (where the map would render).

**Why no bulk backfill**: only one production user (you). Bulk
generating ~50 strategy maps for historical analyses isn't worth the
infra setup. Inline regenerate is one click per old analysis the user
cares about.

**Endpoint**: `POST /api/analysis/{id}/strategy-map/regenerate`. This is
the ONE piece of API surface that survives from the on-demand
architecture. It's NOT the on-demand worker pattern — it triggers an
in-pipeline rerun of the existing analysis. Implementation: load the
persisted analysis, instantiate a new `RequestExecutor` with just
`GenerateStrategyMap` as a step, run it, write the result back to the
assessment record.

The endpoint can run inside the existing API Lambda (it's a single
~35 s strategy-map run; well under the API Lambda's timeout envelope).
Or, if API-Lambda timeout is tight, it can be fronted by a small
"regenerate" SQS message routed to the analysis worker. Decision
deferred to implementation — defaults to in-API-Lambda unless timing
shows otherwise.

### 6. Legacy code removal — both Layer A and Layer B in one phase

**Decision**: Once pipeline integration ships, immediately delete:

**Layer A** (on-demand strategy map):
- `backend/src/handlers/strategy_map_worker_entry.py`
- `backend/src/handlers/strategy_map_handler.py`
- `backend/src/handlers/strategy_map_hydration.py`
- `backend/tests/unit/handlers/test_strategy_map_*` (entire suite)
- `infrastructure/stacks/strategy_map_construct.py`
- API endpoint `POST /api/analysis/{id}/strategy-map`
- Frontend: `StrategyMapCTA`, `StrategyMapGeneratingPlaceholder`,
  `DeepDiveCTA`, `useStrategyMapSubscription`, AppSync subscription
  wiring for `strategy_map_progress` / `strategy_map_complete`.

**Layer B** (decomposition feature flags + monolithic fallback):
- `GENERATE_STRATEGY_MAP_DECOMPOSED` env var check
- `GENERATE_STRATEGY_MAP_DECOMPOSED_SYNTHESIS` env var check
- `_strategy_map_legacy_steps.py` (entire file)
- The flag-layering guard in `GenerateStrategyMap.execute()`
- The conditional dispatch to legacy step runners

**Why both together**: they overlap in spirit ("strategy map shouldn't
have multiple paths anymore"). Splitting the cleanup risks leaving a
half-cleaned state that's harder to reason about. The diff is large
but mostly deletions.

### 7. Phased rollout strategy

**Decision**: Phase the implementation into 5 sequential PRs tracked
under this one change, in dependency order:

```
Phase 1: Canvas layout overhaul                ← Frontend-only; quick win
   Risk: low. No backend changes.

Phase 2: Remove What's Missing                  ← Independent; small
   Risk: low. Pydantic backward-compat for old data.

Phase 3: Pipeline integration + on-demand removal (Layer A)
   Risk: medium. Largest diff; coordinated frontend + backend +
   infrastructure changes.

Phase 4: Narrative reorder + CTA consolidation
   Risk: low. Frontend-only after Phase 3 lands.

Phase 5: Legacy code cleanup (Layer B)         ← Last; pure deletion
   Risk: low. No behavioural change once the flags are removed
   (decomposed is already the only used path in production).
```

Each phase is a separate PR. Each phase ships to staging → testing →
production via the existing promotion flow before the next phase
starts. (Or in batch: testing soak for the full set if you prefer.)

**Why this order**: Phase 1 and Phase 2 are independent quick wins
that improve the existing on-demand experience while we build the
pipeline integration. Phase 3 is the structural shift. Phase 4 is the
narrative polish that depends on Phase 3 (the slot's state machine
changes). Phase 5 is pure cleanup.

## Risks / Trade-offs

- **Total scan latency increases by ~25 s** → Acceptable. The
  strategy map is delivered with the analysis instead of requiring a
  separate click + 45 s wait. Net user-time-to-value improves.
  **Mitigation**: monitor `GenerateStrategyMap` step timings in the
  analysis worker; revisit if the p99 creeps above 60 s.
- **Failure modes change** → Under on-demand, a failed strategy map
  showed a "Generation failed" state in its own slot; the analysis
  itself remained valid. Under pipeline integration, a failed
  strategy-map step fails the WHOLE analysis (modulo whatever
  ``RequestStep`` error handling is in place).
  **Mitigation**: wrap `GenerateStrategyMap.execute()` in a tolerant
  error handler that records the failure on the assessment record
  but allows `PersistResults` to proceed with the rest of the analysis
  data intact. The analysis-detail page then renders the regenerate
  affordance (same as the old-analysis case).
- **Lambda envelope** → The analysis worker's existing timeout/memory
  configuration must comfortably absorb the strategy-map step. Today
  the strategy-map worker has timeout 900 s and memory 2048 MB; the
  analysis worker has been at timeout 540 s / memory 1769 MB (per
  Phase 1/2 alignment) and the analysis itself takes ~120 s clean.
  Adding 35 s of strategy map keeps us at ~155 s — well within 540 s.
  **No envelope changes needed**; the analysis worker's existing
  config absorbs the new step.
- **The decomposed strategy-map AI fan-out (~96 parallel arrow calls)
  runs within the analysis worker** → Means the analysis worker now
  needs OpenAI tier ≥3 (same as today's strategy-map worker). The
  analysis worker already exercises high concurrency on
  `ParallelProfileRiskAndIdeation`, so this is no new constraint.
- **Frontend "expanded by default" CTA** → The legacy
  `Sc0redCTABanner` may or may not have an `expanded` prop today.
  **Mitigation**: add the prop with a default that preserves existing
  call-site behaviour; the Beat 4 mount site opts in.
- **Old-analysis regenerate endpoint** → If implemented in-API-Lambda
  (default), the API Lambda's timeout becomes a constraint. ~35 s for
  strategy-map regeneration plus DynamoDB latency. The API Lambda
  defaults to a 30 s timeout in many serverless setups.
  **Mitigation**: check the actual API Lambda timeout in
  `infrastructure/stacks/janus_stack.py` before implementation. If
  <60 s, route the regenerate request through an SQS message to the
  analysis worker instead.

## Migration Plan

The change ships as 5 phased PRs:

1. **Phase 1 (canvas layout)**: frontend-only. Deploy to staging,
   verify on existing analyses, promote testing → production.
2. **Phase 2 (remove What's Missing)**: backend + frontend. Backward
   compatible with persisted data. Deploy through environments.
3. **Phase 3 (pipeline integration + Layer A cleanup)**: the
   structural change. Pre-cutover: confirm the on-demand worker has
   no in-flight messages (drain the SQS queue). Deploy:
   - Backend pipeline step added.
   - On-demand worker code deleted.
   - CDK construct deleted.
   - Frontend slot simplified.
   - API endpoint deleted; regenerate endpoint added.
4. **Phase 4 (narrative reorder)**: frontend-only. Deploy through
   environments.
5. **Phase 5 (Layer B cleanup)**: backend-only. Pure deletion of
   feature flags and `_strategy_map_legacy_steps.py`. Deploy through
   environments.

**Rollback**: each phase is independently revertable via the standard
git-revert flow. The phases are designed so that a partial rollback
of one phase doesn't break the others.

2. **`Sc0redCTABanner` expanded-by-default visual design** — the

3. **Tolerant error handling for the pipeline step** — should a failed
   strategy map block the WHOLE analysis, or be a recorded soft
