## ADDED Requirements

### Requirement: Streamable HTTP transport endpoint
The MCP server SHALL use Streamable HTTP transport via `POST /mcp` for all MCP protocol communication. The server SHALL be built using FastMCP's `streamable_http_app()` wrapped with Mangum for Lambda deployment.

#### Scenario: Authenticated client sends MCP request
- **WHEN** a client sends POST to `/mcp` with a valid OAuth Bearer token and JSON-RPC body
- **THEN** the server processes the request and returns a JSON-RPC response

#### Scenario: Unauthenticated client sends MCP request
- **WHEN** a client sends POST to `/mcp` without a valid token
- **THEN** the server returns 401 with WWW-Authenticate header pointing to Protected Resource Metadata

### Requirement: SDK-managed OAuth endpoints
The MCP server SHALL use the `OAuthAuthorizationServerProvider` interface from the `mcp` Python SDK. The SDK SHALL auto-mount the standard OAuth endpoints: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/register`, `/authorize`, `/token`, `/revoke`.

#### Scenario: OAuth metadata discoverable
- **WHEN** a client fetches `/.well-known/oauth-protected-resource`
- **THEN** the server returns RFC 9728 metadata pointing to the authorization server

#### Scenario: OAuth authorization server metadata
- **WHEN** a client fetches `/.well-known/oauth-authorization-server`
- **THEN** the server returns RFC 8414 metadata with all endpoint URLs

### Requirement: OAuthAuthorizationServerProvider implementation
Janus SHALL implement the `OAuthAuthorizationServerProvider` interface with DynamoDB-backed storage for clients, codes, tokens, and refresh tokens.

#### Scenario: get_client returns registered client
- **WHEN** the SDK calls `get_client(client_id)` for a registered client
- **THEN** the provider returns client info from DynamoDB OAUTH_CLIENT# records

#### Scenario: register_client creates new client
- **WHEN** the SDK calls `register_client()` with DCR request data
- **THEN** the provider stores the client in DynamoDB and returns the client_id

#### Scenario: verify_access_token validates JWT
- **WHEN** the SDK calls `verify_access_token(token)` with a valid Janus-issued JWT
- **THEN** the provider verifies signature and expiry, returns AuthInfo with user_id, org_id, role

### Requirement: Tool listing
The MCP server SHALL respond to `tools/list` with all available tools, their descriptions, and input schemas (auto-generated by FastMCP from Python type hints).

#### Scenario: Client requests tool list
- **WHEN** a client sends `tools/list` via JSON-RPC
- **THEN** the server returns all registered tools with name, description, and JSON Schema

### Requirement: Tool invocation
The MCP server SHALL respond to `tools/call` by executing the named tool with provided arguments and returning the result.

#### Scenario: Valid tool call
- **WHEN** a client sends `tools/call` with a valid tool name and arguments
- **THEN** the server executes the tool and returns the result as content blocks

#### Scenario: Unknown tool
- **WHEN** a client sends `tools/call` with a non-existent tool name
- **THEN** the server returns a JSON-RPC error indicating the tool was not found

### Requirement: Rate limiting
The MCP server SHALL enforce per-user rate limits: 100 read operations/minute, 5 scan operations/hour, 30 scan operations/day per org.

#### Scenario: Rate limit exceeded
- **WHEN** a user exceeds the read rate limit
- **THEN** the server returns an error with a retry-after indication

### Requirement: Audit logging
The MCP server SHALL log every tool invocation with user_id, org_id, client_id, tool_name, timestamp, and success/failure status.

#### Scenario: Tool call logged
- **WHEN** any tool is invoked
- **THEN** an audit record is written with the invocation details
